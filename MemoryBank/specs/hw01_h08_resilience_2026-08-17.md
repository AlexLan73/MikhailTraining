## 1. Сценарий 1 — прерывание пользователем (главная находка)

### 1.1 Как воспроизводится

Настоящий `Ctrl+C` дочернему процессу на Windows из скрипта **не доставить**, и это проверено:

| Приём | Результат |
|---|---|
| Git-Bash `kill -INT <pid>` | до нативного python не доходит: процесс дорабатывает прогон до конца, bash лишь помечает задание как «signalled» (130) |
| `CREATE_NEW_PROCESS_GROUP` + `CTRL_C_EVENT` | ребёнок событие игнорирует (проба: не завершился за 6 с) |
| `CREATE_NEW_PROCESS_GROUP` + `CTRL_BREAK_EVENT` | процесс убит мгновенно кодом `0xC000013A`, обработчик Python не вызывался — это не `Ctrl+C` |
| `CREATE_NEW_CONSOLE` + `AttachConsole` + `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` | вызовы успешны, но прогон завершился штатно (код 1): событие до ребёнка не дошло |
| `_thread.interrupt_main()` из потока-таймера | флаг ставится, но **заблокированное** ожидание `queue.join()` не будится: исключение поднимается только когда `join()` вернулся сам |

Поэтому прерывание воспроизводится в **той же точке кода**, куда его приводит живой `Ctrl+C`
на Windows (ожидание блокировки в главном потоке прерывается событием SIGINT): подменяется
`queue.Queue.join` так, что первый вызов поднимает `KeyboardInterrupt`. Проба лежит в
рабочем каталоге сессии (не в репозитории), сама команда прогона — обычная:

```bash
python -m core.mdscan out/hw01/h08/big -scan.respect_gitignore:false \
  -logging.dir:out/hw01/h08/join -report.dir:out/hw01/h08/join -report.console:false
```

Дерево цели: `FixtureTreeBuilder().generated(Path('out/hw01/h08/big'), 3000, 42)` — 3000 файлов,
5935 ссылок, из них 2/3 внешние (`https://example.org/gen/*`), HTTP включён (это и делает
прогон достаточно долгим, чтобы прерывание имело смысл: полный прогон ≈ 16 с).

### 1.2 Дефект Д-H08-1 (исправлен)

**Что было.** `KeyboardInterrupt` — не `Exception`, поэтому его не ловил ни
`ScanOrchestrator.scan` (`except Exception`), ни `main` (`except Exception`). Последствия
измерены, все четыре сразу:

1. исключение выходило наружу трейсбеком — человек видел стек, а не сообщение;
2. `finally` фазы 3 срабатывал **раньше**, чем заканчивали воркеры: лог закрывался, и записи
   `parse-*` уходили на stderr «сырыми» (`logging.lastResort`) — в файле лога их нет
   (замер: в логе осталось 35 строк, дальше поток шёл на stderr);
3. очередь **не отбрасывалась**: 10 не-демонов дорабатывали все 2980 оставшихся файлов с
   HTTP-проверками, процесс жил > 2 мин (в замере убит по таймауту) — вместо ожидаемых ≤ 5 с;
4. отчёта нет, кода возврата в POSIX-смысле нет.

**Что стало** (тот же прогон, то же место прерывания):

```text
код возврата: 130
прерван на 0.49 с, гашение заняло 0.32 с
потоки прогона живы: []
лог: «прерывание: отброшено необработанных задач 2980»
     «конвейер остановлен: результатов 20»
     CRITICAL «прогон прерван пользователем (Ctrl+C): отчёт не записан;
                найдено файлов 3000, разобрано 20, ссылок 36»
```

Общее время жизни процесса — 1.18 с (было > 120 с).

### 1.3 Что именно изменено (минимальная правка)

| Файл | Правка |
|---|---|
| `core/mdscan/runtime/pipeline_runner.py` | `cancel()` — отбрасывает необработанные задачи и возвращает их число; `_await_tasks()` — ожидание `TaskQueue.join()` с перехватом `KeyboardInterrupt` (отбросить остаток → дождаться выхода воркеров); `run()` перехватывает прерывание обхода и помечает прогон (`interrupted`), не выпуская исключение наружу — гашение по сентинелам обязано состояться |
| `core/mdscan/runtime/scan_orchestrator.py` | `INTERRUPTED_CODE = 130`; `pipeline.interrupted` → `_interrupted(summary)`: `CRITICAL` + счётчики + код 130 **без** файла отчёта; отдельный `except KeyboardInterrupt` как страховка для фаз 0/2 |
| `core/mdscan/__main__.py` | `except KeyboardInterrupt` → строка «прервано пользователем (Ctrl+C)» в stderr + код 130; коды возврата в докстринге дополнены |

Инварианты сохранены осознанно, это записано в докстрингах:

- **сентинелы не съедаются** — `cancel()` возвращает встреченный `END_DISCOVERY` в очередь,
  иначе parse-worker навсегда останется на `get()` (инвариант 19);
- **баланс `task_done()`** — на каждый снятый элемент вызывается свой `task_done()`, поэтому
  `TaskQueue.join()` после отбрасывания возвращается (инвариант 5);
- **порядок гашения D1 не тронут** — отбрасывание вставлено внутрь ожидания, шаги
  `join → worker.join → END_RESULTS → results.join → collector.join` идут как были;
- **потоков не остаётся** — проверено и тестом, и ручным прогоном (`threading.enumerate()`).

### 1.4 Что осталось на решение Alex

1. **Код 130 не описан в спеке** (§1.4 архитектуры: 0/1/2/3). Взят как POSIX-соглашение
   `128 + SIGINT` по прямому указанию в ТЗ H-08; с 0/1/2/3 не конфликтует, но формально это
   расширение CLI-контракта — нужно внести в §1.4 и в `Doc/Modules/mdscan/CLI.md` (H-12).
2. **Отчёт по прерванному прогону не пишется** (выбран «явное сообщение» из двух вариантов
   ТЗ). Причина: неполные числа в файле отчёта невозможно отличить от полных. Счётчики
   уходят в лог и в `ScanSummary`, так что ДЗ (`metrics.json`) их видит.
3. **Прерывание на стадии обхода** ждёт завершения уже запущенных `discover`-потоков
   (`ThreadPoolExecutor.__exit__` → `shutdown(wait=True)`). На локальном дереве это доли
   секунды, но на клонировании организации (`clone_workers`) может занять столько, сколько
   идёт текущий `git clone`. Прерывать сам клон — отдельное решение (Д-H13-подобное).
4. **Второй `Ctrl+C`** во время гашения выпускается наружу и превращается в код 130 без
   отчёта (страховочный `except` оркестратора); потоки в этом случае могут остаться —
   сознательный компромисс «пользователь настаивает».

## 2. Сценарий 2 — нет сети (ручной)

```bash
HTTPS_PROXY=http://127.0.0.1:9 HTTP_PROXY=http://127.0.0.1:9 \
python -m core.mdscan out/hw01/h03 -scan.respect_gitignore:false -http.timeout_ms:500 \
  -logging.dir:out/hw01/h08/nonet -report.dir:out/hw01/h08/nonet -report.console:false
```

| Показатель | Значение |
|---|---|
| Код возврата | 1 (битые есть) |
| Время | 5.71 с (`duration_sec` в отчёте — то же) |
| Ссылки | 45 всего: local 6 (3 ok / 3 broken), github 12 (все `TIMEOUT`), url 27 (все `TIMEOUT`) |
| `timeout_http` / `broken_http` | 39 / 0 |
| `ERROR` / `CRITICAL` в логе | 0 |

Выводы:

- отсутствие сети **не смешивается** с `BROKEN`: мёртвый прокси на 127.0.0.1:9 не отвечает
  вовсе (SYN гасится), значит исход честно `TIMEOUT` с кодом 0 — требование T11/T12 держится;
- локальные проверки при мёртвой сети работают как обычно, прогон доходит до отчёта;
- **формула времени из ТЗ (`N_url × timeout / http.workers`) не выполняется** и не должна:
  ссылки одного файла проверяются **последовательно** внутри своего parse-worker'а, а
  `http.workers` — только потолок одновременных запросов. Три файла-копии шли в лок-степ по
  одним и тем же URL (кэш на URL), поэтому фактическое время = 11 различных URL × 0.5 с ≈ 5.5 с.
  Параллельность по HTTP проявляется на **разных** URL в разных файлах (это и мерил H-07).
