### D1. Потоки или asyncio

- Варианты: (A) `ThreadPoolExecutor`, (B) `asyncio`, (C) `multiprocessing`.
- **Выбор: A**, потоки: стадия 1 — `ThreadPoolExecutor(workers.discover)`; стадия 2 — `workers.parse`
  именованных потоков `MarkdownWorker(BaseObserver)`; HTTP — **семафор** `http.workers` внутри
  parse-worker'а, отдельных http-потоков нет (C2, вариант A). Размеры из конфига, 5 — только
  значение по умолчанию (D3.2). 🔧 ревью 3: было «по пулу на стадию, включая http».
- Почему: все операции ядра синхронные и I/O-bound (`ls-files`/`rglob`, `read_text`, GitPython).
  В asyncio их пришлось бы заворачивать в `to_thread` — сложность вверх, выгода нулевая.
  `multiprocessing` даст накладные расходы на сериализацию результатов и убьёт общий `EventBus`.
- Следствия: GIL нам не мешает (ждём диск, не считаем); если позже появится массовая HTTP-проверка
  сотен URL — можно добавить **отдельный** асинхронный чекер, не трогая ядро (Protected Variations).
- Тест: инвариант «результатов ровно столько, сколько задач» + ошибка одного файла не роняет остальные.

### D2. Общая шина: `queue.Queue`, создаётся оркестратором и передаётся через DI (Singleton не нужен)

- Варианты: (A) worker возвращает результат в главный поток, главный пишет;
  (B) worker сам публикует в общую очередь.
- **Выбор: B** (прямое требование размышлений и правильное с точки зрения связности).
- Почему: главный поток не становится узким местом и «богом»; producer владеет своим результатом.
- Важно и записано явно: **потокобезопасность даёт `queue.Queue`** — ни `Lock`, ни Singleton

- 🔧 **ревью 2 — Singleton `EventBus` снят.** Раньше здесь стоял Singleton за `EventBusProtocol`

  Глобального состояния нет → нечего сбрасывать между тестами, `reset()` не нужен. Имя `EventBus`
  в коде не используется — есть `TaskQueue` и `ResultQueue` (`runtime/queues.py`).
- Тест: два прогона подряд не видят чужих результатов; N producer-потоков → N результатов у Observer.

#### 🔄 D2.1 Сквозное правило проекта: перехват исключений + максимальное логирование

> Требование Alex — относится **ко всему проекту**, не только к шине.

**Правило перехвата.** Ни одно исключение не уходит «в никуда»:

| Уровень | Что делаем |
|---|---|
| Внутри worker'а (обработка одного файла) | `except Exception as exc` → лог `ERROR` с трейсом → **публикуем событие с ошибкой** → поток продолжает работу |
| Внутри потока-обхода (репозиторий) | так же: репозиторий помечается ошибочным, остальные обходятся |
| Внутри Observer/Reporter | лог `ERROR`, обработка следующего события; падение потребителя = потеря отчёта, поэтому его тело целиком под защитой |
| Главный поток | `except` вокруг всего прогона → лог `CRITICAL` + понятное сообщение + код возврата `3` |
| Никогда | «голый» `except:` и `except Exception: pass` — запрещены (правило 05) |

**Что логируем (обязательный минимум).** Логируется каждый шаг конвейера, а не только ошибки:

| Событие | Уровень | Пример строки |
|---|---|---|
| Старт: конфиг, входной путь, число потоков, включённые проверки | `INFO` | шапка лога (D9) |
| Найден репозиторий | `INFO` | `repo=lib-a root=vendor/lib-a nested=yes remote=git@…` |
| Найден `.md` (в очередь) | `DEBUG` | `queued file=docs/install.md repo=project` |
| Взят в обработку потоком | `DEBUG` | `parse-start thread=parse-2 file=…` |
| Файл разобран | `INFO` | `parsed file=… links=5 elapsed=3.1ms` |
| **Каждая ссылка** — хорошая | `DEBUG` | `link OK kind=local target=docs/a.md file=…` |
| **Каждая ссылка** — битая | `WARNING` | `link BROKEN kind=url http=404 target=… file=… line=12` |
| Ошибка чтения/разбора/git | `ERROR` | с типом исключения и трейсом |
| Дубль отсечён реестром (D6.4) | `DEBUG` | `duplicate skipped file=…` |
| Итоги прогона | `INFO` | сводка теми же числами, что в отчёте |

- Каждая ссылка в лог — это на 10 000 файлов сотни тысяч строк `DEBUG`. Поэтому: **уровень

- ✅ Логгер **включён по умолчанию**, есть ключ отключения (`logging.enabled: false` в конфиге).
- Формат строки и имя файла — D9. Многопоточность — `QueueHandler`/`QueueListener` (D9).

### D3. Сентинелы конца стадий (`END_DISCOVERY`, `END_RESULTS`)

- Варианты: `None` / `0` / `""` / уникальный объект / отдельный тип события.
- **Выбор**: уникальные объекты своего типа (`END_DISCOVERY = _EndDiscovery()`,
  `END_RESULTS = _EndResults()`), см. D3.1. 🔧 ревью 2: старое имя `END_OF_STREAM` убрано.
- Почему: `None`/`0`/`""` могут совпасть с настоящими данными → тихая остановка Observer.
- Тест: публикация результата с «пустыми» полями не завершает Observer; сентинел — завершает;
  сентинелы не путаются местами; прогон с прогрессом и без него даёт одинаковый отчёт.

🔄 **Переработано по замечанию Alex: конвейер двухстадийный, а не одностадийный.**

#### D3.1 Две стадии — две очереди — два сентинела

Твоё видение принято полностью. Раньше в спеке была одна очередь; правильная схема:

```text
СТАДИЯ 1 — поиск .md                        СТАДИЯ 2 — разбор .md
┌─────────────────────────────┐             ┌──────────────────────────────┐
│ discover_workers потоков    │             │ parse_workers потоков        │
│ по репозиторию на поток     │             │ по файлу на поток            │
│  → TaskQueue.put(md_task)   │             │  → ResultQueue.put(result)   │
└──────────┬──────────────────┘             └──────────┬───────────────────┘
           │ все репозитории обойдены                  │ все файлы разобраны
           ▼                                           ▼
   TaskQueue.put(END_DISCOVERY)               ResultQueue.put(END_RESULTS)
           │                                           │
           ▼                                           ▼
   потребитель стадии 2 знает:                 Reporter знает:
   новых файлов больше не будет                новых результатов не будет
                                                       │
                                                       ▼
                                               лог + консоль + отчёт
```

- **Два разных сентинела**, не один: `END_DISCOVERY` (конец поиска файлов) и `END_RESULTS`
  (конец разбора). Один общий объект на две очереди — источник путаницы при отладке.
- Стадия 2 **не ждёт** окончания стадии 1: первый найденный файл сразу уходит в разбор.
  Это и есть выигрыш конвейера — на большом наборе репозиториев поиск и разбор идут внахлёст.
- **Главный поток ждёт только модуль вывода** (`reporter.join()`) — как ты и написал.

🔧 **ревью 2 — три пробела, которые макет M1 обязан закрыть (иначе тихая потеря данных):**

| # | Пробел | Правило |
|---|---|---|
| 1 | `parse_workers` потоков читают **одну** `TaskQueue`, а `END_DISCOVERY` один | главный поток кладёт **по сентинелу на каждый parse-worker** (`N` штук) — тогда каждый worker гарантированно получает свой и выходит; на сентинел тоже вызывается `task_done()` |
| 2 | Гонка `task_done()` ↔ `put(result)` | worker вызывает `TaskQueue.task_done()` **только после** `ResultQueue.put(result)`. Иначе `TaskQueue.join()` в главном потоке завершится раньше, чем результат окажется в `ResultQueue`, и `END_RESULTS` уедет вперёд результата |

#### D3.5 Прогресс во время работы

Принято как **опция** (это добавляет параметр в CLI — см. D12):

- отдельный поток `ProgressReporter` с таймером (по умолчанию раз в 1 с);
- показывает: репозиториев найдено, `.md` найдено, разобрано, осталось в `TaskQueue`,
  осталось в `ResultQueue`, ссылок проверено, битых;
- пишет одной перерисовываемой строкой (или `rich.Progress`, если библиотека есть);
- по завершении гасится и не мешает финальной таблице;
- опция выключена → объект не создаётся вообще (Null Object).

🔄 **Уточнение Alex: вывод состоит из ДВУХ зон.**

```text
┌─ ЗОНА 1 — статус процесса (обновляется по таймеру, живёт до конца прогона) ────────┐
│ repos 3/10 · md 128/… · parsed 96 · queue task=32 result=4 · links 640 · broken 7  │
└───────────────────────────────────────────────────────────────────────────────────┘
  ЗОНА 2 — сообщения модулей (любой модуль пишет строку; строка стирается через 5 сек)
  [parse]  docs/install.md — 12 ссылок
  [http]   https://example.org — 404
```

| Зона | Кто пишет | Как обновляется | Время жизни |
|---|---|---|---|
| **1. Статус процесса** | `ProgressReporter` по таймеру | перерисовка на месте (`interval_sec`) | весь прогон |
| **2. Строка сообщения** | **любой модуль** через общий интерфейс | новая строка вытесняет старую (перезапись) | **5 секунд**, потом стирается |

Правила зоны 2:
- интерфейс один на всех: `notifier.show(text)` — модуль не знает, куда и как это рисуется
  (Null Object, если вывод выключен);
- строк одновременно — фиксированное число (по умолчанию **1**, настраивается);
- через `message_ttl_sec` строка гаснет сама, даже если новых сообщений нет — экран не «залипает»
  на старом сообщении;
- сообщение всегда дублируется в лог (лог — полный, экран — только последнее).

```yaml
progress:
  enabled: true             # показывать блок прогресса
  interval_sec: 1.0         # период перерисовки статуса (зона 1)
  style: line               # line — компактная строка | panel — рамка | off
  message_lines: 1          # сколько строк-сообщений держим (зона 2)
  message_ttl_sec: 5        # через сколько секунд строка стирается
```

Реализация: с `rich` — `Live` с группой «статус + сообщения»; без `rich` — ANSI (сохранение
позиции курсора и перерисовка N строк). Обе — за одним интерфейсом (D10).

⚠️ Одна перерисовываемая строка (`\r`) конфликтует с обычным выводом в тот же поток: если кто-то
напечатает строку — прогресс «размажет». Поэтому: **весь вывод прогресса идёт в `stderr`,
финальные таблицы и отчёт — в `stdout`**. Тогда `> file.txt` даёт чистый результат без мусора,
а при неинтерактивном запуске (не TTY) прогресс автоматически отключается.

⚠️ Оговорка: `queue.qsize()` — **приблизительное** значение (без гарантий согласованности).
Для прогресса этого достаточно, но **логику завершения на нём строить нельзя** — только сентинелы.

### D6. Дедупликация nested-поддеревьев

🔄 **Расписано подробно — по твоей просьбе «докажи, я не понял».**

#### D6.1 В чём вообще проблема (на конкретном дереве)

Git-репозиторий может физически содержать внутри себя **другой** git-репозиторий: submodule,
или просто клон, который кто-то сделал внутрь рабочей папки. Пример:

```text
project/                      ← главный репозиторий, .git — КАТАЛОГ
├── .git/
├── README.md                          (1)
├── docs/
│   ├── install.md                     (2)
│   └── api.md                         (3)
└── vendor/
    └── lib-a/               ← ВЛОЖЕННЫЙ репозиторий, .git — ФАЙЛ (submodule)
        ├── .git             (файл: "gitdir: ../../.git/modules/lib-a")
        ├── README.md                  (4)
        └── doc/guide.md               (5)
```

Мы делаем два независимых действия:

1. «Собери список репозиториев» → получаем **два**: `project` и `project/vendor/lib-a`.
2. «Для каждого репозитория найди все `.md`» → и вот здесь ловушка:

| Репозиторий | Наивный обход `rglob("*.md")` | Что получилось |
|---|---|---|
| `project` | (1) (2) (3) **(4) (5)** | залез в чужое поддерево |
| `project/vendor/lib-a` | (4) (5) | правильно |
| **Итого задач** | **7**, хотя файлов **5** | (4) и (5) обработаны **дважды** |

Последствия дублей: `md_files_total` = 7 вместо 5 → счётчик ссылок завышен вдвое по этим файлам →
в отчёте один и тот же файл двумя строками (в одной `repo=project`, в другой `repo=lib-a`) →
одна и та же битая ссылка посчитана дважды. Плюс лишняя работа: на 10 000 файлов это лишние часы.

#### D6.2 Правило и почему оно работает

> Главный репозиторий сканирует своё дерево, **исключая поддеревья вложенных репозиториев**.
> Каждый вложенный сканирует своё дерево сам.

Формально: файл принадлежит **ближайшему вверх по дереву** git-корню. Ровно так же считает и сам
git: файлы submodule не входят в `git ls-files` родителя.

Для примера выше:

| Файл | Ближайший git-корень вверх | Кто его сканирует |
|---|---|---|
| `project/README.md` | `project` | главный |
| `project/docs/install.md` | `project` | главный |
| `project/vendor/lib-a/README.md` | `project/vendor/lib-a` | вложенный |
| `project/vendor/lib-a/doc/guide.md` | `project/vendor/lib-a` | вложенный |

Каждый файл считается ровно один раз, потому что «ближайший корень» — **единственный**.
Это и есть доказательство: множество файлов разбивается на непересекающиеся подмножества.

#### D6.3 Почему «фильтр по префиксу пути», а не «по имени каталога»

Наивная реализация — «пропускать каталог, если он называется `vendor` / `libs` / `third_party`».
Так делать нельзя: имя ничего не гарантирует. Правильно — сравнивать **путь целиком**:

```python
# nested_roots = [Path("project/vendor/lib-a"), ...]  — абсолютные, разрешённые
def belongs_to_main(md_file: Path, nested_roots: list[Path]) -> bool:
    return not any(md_file.is_relative_to(root) for root in nested_roots)
```

`Path.is_relative_to()` — это и есть проверка префикса пути (stdlib, Python ≥ 3.9).
Почему именно так:

| Случай | Проверка по имени | Проверка по префиксу |
|---|---|---|
| `project/vendor/lib-a/README.md` при nested `vendor/lib-a` | пропустит (имя совпало) | пропустит ✅ |
| `project/vendor/notes.md` (файл рядом с nested, но **не в нём**) | **ошибочно пропустит** ❌ | оставит главному ✅ |
| Вложенный называется `docs` (совпадает с обычной папкой в другом месте) | **ошибочно выкинет чужие docs** ❌ | выкинет только реальный nested ✅ |
| Symlink / другой регистр пути на Windows | непредсказуемо | разрешаем `Path.resolve()` до сравнения ✅ |

#### D6.4 Твоё предложение про реестр — принимаю, и оно решает **вторую** задачу

> Alex: «мы можем вести потоко-независимый реестр, в котором будут записываться пути:
> `https://github.com/dsp-gpu` — корневой, `.../radar` — проверяемый, `.../radar/blob/main/README.md` — файл».

Да, берём — но это **не замена** правилу D6.2, а дополнение. Разведём две вещи, чтобы не путались:

| Механизм | Что решает | Когда срабатывает |
|---|---|---|
| **Правило ближайшего корня** (D6.2) | чтобы дубль **не появился** | на этапе поиска файлов |
| **Реестр обработанных** (твоё) | чтобы дубль **не прошёл дальше**, если всё-таки появился | на этапе постановки задачи в очередь |

Реестр как страховка нужен обязательно — есть случаи, где правила недостаточно: symlink на другую
папку, два worktree одного репозитория, один и тот же репозиторий, попавший в список дважды.

Контракт реестра (`ProcessedRegistry`, потокобезопасный — `set` под `Lock`):

```python
key = (repo_root_resolved, md_file_resolved)   # ключ — пара, а не только файл
if not registry.add_if_absent(key):
    logger.debug("дубль пропущен: %s", md_file)
    return                                      # в очередь НЕ кладём
```

Твоя тройка «корневой / проверяемый / файл» ложится сюда напрямую:

| Уровень | Локальный вход | GitHub-организация (D3.3) |
|---|---|---|
| корневой | `project/` | `https://github.com/dsp-gpu` |
| проверяемый (репозиторий) | `project/vendor/lib-a` | `https://github.com/dsp-gpu/radar` |
| файл | `vendor/lib-a/doc/guide.md` | `.../radar/blob/main/README.md` |

Это же трио идёт в отчёт и в лог — тогда любую строку отчёта можно кликнуть/проверить руками.
На 10 000 файлов реестр — это ~10 000 кортежей в памяти, единицы мегабайт. Приемлемо.

- Тесты: (а) файл nested-репо попадает в задачи ровно один раз; (б) `project/vendor/notes.md`
  **не** теряется; (в) повторная подача того же репозитория в источник не создаёт вторых задач;
  (г) symlink на уже просканированную папку не даёт дублей.

#### D7.2 Почему это снимает главный риск

Три вещи, на которых regex-парсер съел бы дни отладки, у `markdown-it-py` **не существуют как проблема**:

1. **Fenced/inline code.** Содержимое ``` code ``` попадает в токен `fence`/`code_inline` и
   **не порождает link-токенов вообще**. Отдельный `CodeBlockMasker` (который я закладывала) —
   больше не нужен, минус класс и минус источник багов.
2. **Reference-ссылки** `[текст][id]` + `[id]: docs/a.md`. Парсер сам сопоставляет метку с
   определением и выдаёт готовый `href`. На regex это отдельный проход с собственным словарём меток.
3. **Номер строки** ссылки для отчёта — `token.map` у блочного токена, без ручного подсчёта `\n`.

### D8. Классификация ссылок — цепочка правил (🔄 расписано подробно)

#### D8.1 Зачем вообще классифицировать

Парсер (D7) отдаёт только **строку-цель**: `docs/a.md`, `#install`, `https://github.com/org/repo`,
`mailto:a@b.c`. Что с ней делать дальше — зависит от её **вида**:

| Вид (категория) | Пример | Кто и как проверяет |
|---|---|---|
| `LOCAL` | `docs/a.md`, `../img/x.png`, `file:///C:/tmp/a.md` | проверка существования файла на диске (относительно **файла-владельца**) |
| `ANCHOR` | `#install` | проверка, что такой заголовок есть в этом же файле |
| `GITHUB` | `https://github.com/org/repo`, `raw.githubusercontent.com`, `gist.github.com` | HTTP-проверка + отдельная секция отчёта (нам это интересно как проекту) |
| `URL` | `https://example.org/a` | HTTP-проверка |
| `MAILTO` | `mailto:alex@example.org` | не проверяем, только считаем |
| `TEL` | `tel:+7999…` | не проверяем, только считаем |
| `WIKILINK` | `[[Внутренняя страница]]` (плагин `wikilinks`, D7.1) | v1: считаем и логируем, `NullChecker` |
| `FOOTNOTE_URL` | URL внутри сноски `[^1]: https://…` (плагин `footnote`, D7.1) | v1: считаем и логируем, `NullChecker` |
| `UNKNOWN` | всё, что не подошло | попадает в лог `WARNING`, в отчёт отдельной строкой |

wikilink | footnote`), а правило получает **`MdLink`**, а не голую строку: `matches(link)`.

Ещё один случай, который таблица не покрывала: **локальная ссылка с якорем** `docs/a.md#install`.
Категория — `LOCAL`; при `checks.anchors: true` после проверки файла проверяется и заголовок
в **целевом** файле (`AnchorChecker`, часть 2 C3). `#install` без пути — `ANCHOR`, тот же файл.
🔧 ревью 3 — правило сравнения якоря (нигде не было записано): заголовок → **GitHub-slug**
(нижний регистр, пробелы → `-`, пунктуация убирается, кириллица сохраняется, повтор → `-1`, `-2`),

Поэтому сигнатура чекера — `check(link, md_file)`, а не `check(link, base_dir)`: якорному чекеру нужен
сам файл.

То есть категория определяет **маршрут** ссылки дальше. Без неё пришлось бы разбираться в типе
внутри каждого чекера — то есть трижды.

#### D8.2 Как это выглядит без паттерна (и почему плохо)

```python

    elif target.startswith("mailto:"):

    elif target.startswith("tel:"):

    elif "github.com" in target or "githubusercontent" in target:

Проблемы, которые вылезут на реальном репозитории:
- добавили категорию (например `WIKILINK` для Obsidian `[[…]]`) → **правим существующую функцию**,
  рискуя сломать работающие ветки. Это прямое нарушение Open-Closed (правило 09);
- порядок веток невидимо важен (`github` обязан идти **до** `url`, иначе все GitHub-ссылки станут
  просто `URL`), но нигде не зафиксирован — забудешь и не заметишь;
- каждую ветку нельзя протестировать отдельно — только функцию целиком;
- функция растёт и превращается в «ту самую» простыню.

#### D8.3 Как делаем: Chain of Responsibility

Одна ветка = один класс = один файл. Классы выстроены в **явный список** — порядок виден глазами:

```python
# core/mdscan/parsing/rules/link_rule.py
class LinkRule(Protocol):
    def matches(self, link: MdLink) -> bool: ...   # 🔧 ревью 2: MdLink, а не str — нужен link.origin
    @property
    def kind(self) -> LinkKind: ...

# core/mdscan/parsing/rules/rule_anchor.py
class AnchorRule:
    """Ссылка на заголовок внутри того же файла: '#install'."""
    def matches(self, link: MdLink) -> bool:
        return link.target.startswith("#")
    @property
    def kind(self) -> LinkKind:
        return LinkKind.ANCHOR

# core/mdscan/parsing/link_classifier.py
class LinkClassifier:
    """Первое сработавшее правило определяет категорию. Порядок значим."""
    def __init__(self, rules: Sequence[LinkRule]) -> None:
        self._rules = tuple(rules)

    def classify(self, link: MdLink) -> LinkKind:
        for rule in self._rules:
            if rule.matches(link):
                return rule.kind
        return LinkKind.UNKNOWN            # Null Object: ветки 'else' нет
```

Сборка цепочки — в Composition Root, **порядок задан явно и документирован**:

```python
LinkClassifier([
    WikilinkRule(),    # origin == wikilink  — по синтаксису, раньше всех (🔧 ревью 2)
    FootnoteRule(),    # origin == footnote  — по синтаксису (🔧 ревью 2)
    AnchorRule(),      # '#...'        — самый узкий случай по цели
    MailtoRule(),      # 'mailto:'
    TelRule(),         # 'tel:'
    GithubRule(),      # github.com / raw.githubusercontent.com / gist.github.com
    HttpRule(),        # http:// https://  — ПОСЛЕ GithubRule, иначе перехватит его случаи
    FileUrlRule(),     # 'file:///...'  → LOCAL (требование условия курса)
    LocalPathRule(),   # всё остальное, что похоже на путь
])
```

Итого **9 правил** (было 7) — число сходится с папкой `parsing/rules/` и бюджетом в части 2.

Что мы с этого получаем:

| Плюс | Как проявляется |
|---|---|
| Open-Closed | новая категория = новый файл + одна строка в списке; старые классы не трогаем |
| Тестируемость | у каждого правила свой тест на 3–5 строк; ошибка локализуется мгновенно |
| Порядок стал явным | список — это и есть документация приоритетов; тест «GithubRule до HttpRule» ловит перестановку |
| Нет «else» | `UNKNOWN` (Null Object) — неизвестное не молчит, а попадает в отчёт |
| Правило = имя | в логе видно, какое правило сработало, — отладка без гадания |

- Тест: параметризованная таблица «строка → ожидаемая категория» (включая `file:///…` из условия
  курса); отдельный тест на порядок: GitHub-URL классифицируется как `GITHUB`, а не `URL`.

### D9. Логирование через `QueueHandler` + `QueueListener`

- Почему: worker не должен блокироваться на записи в файл; записи не перемешиваются.
- Формат: `время | уровень | поток | repo | file | сообщение`.
- Отдельная очередь логов, **не** та же, что EventBus: разные жизненные циклы и разные владельцы.
- Тест: из 5 потоков пишем N записей → в файле ровно N строк, ни одной битой.

🔄 **Дополнено: имя файла лога и отчёта (по замечанию Alex).**

Имя формируется из **имени цели** и метки времени старта:

```text
<scope>_<YYYY-MM-DD>_<HH-MM-SS>.log        <scope>_<YYYY-MM-DD>_<HH-MM-SS>.md
```

где `<scope>` — то, что сканируем:

| Вход | `<scope>` | Пример имени лога |
|---|---|---|
| GitHub-организация `https://github.com/dsp-gpu` | `dsp-gpu` | `dsp-gpu_2026-08-16_05-00-12.log` |
| Один удалённый репозиторий `…/AlexLan73/GPUWorkLib` | `GPUWorkLib` | `GPUWorkLib_2026-08-16_05-00-12.log` |
| Локальный репозиторий `…/MikhailTraining` | `MikhailTraining` (имя корневой папки) | `MikhailTraining_2026-08-16_05-00-12.log` |
| Локальная папка без git | имя папки | `notes_2026-08-16_05-00-12.log` |

То есть «пусто» не остаётся никогда — если организации нет, `<scope>` берётся из имени корневого
каталога. Так все имена однотипны, а файлы разных прогонов не перетирают друг друга.

**Шапка лога** (первые строки каждого файла) — заполняется на старте:

```text
# scope       : dsp-gpu (github organization)   |  или: MikhailTraining (local path)
# started     : 2026-08-16 05:00:12 +03:00
# input       : https://github.com/dsp-gpu
# workers     : discover=5 parse=5 http=5
# checks      : local=on http=on nested=on
# report      : out/hw01/dsp-gpu_2026-08-16_05-00-12.md
```

✅ **Решения Alex:**

1. **Аргумент лога и результата — это только КАТАЛОГ** (место, куда писать). Имя файла всегда
   формируем сами по стандарту — пользователь его не задаёт. Это упрощает и валидацию:
   проверяем каталог (существует/создаётся/доступен на запись), а не путь к файлу.
2. **Формат имени — с секундами**: `<scope>_<YYYY-MM-DD>_<HH-MM-SS>.log` / `.md`.
   Два прогона в одну минуту больше не конфликтуют.

Итог по именам:

```text
<logging.dir>/dsp-gpu_2026-08-16_05-00-12.log
<report.dir>/dsp-gpu_2026-08-16_05-00-12.md
```

Каталоги по умолчанию: `out/hw01/` для обоих. Метка времени **одна на прогон** — лог и отчёт
одного запуска имеют одинаковый суффикс, их видно парой в каталоге.

### D12. CLI — 🔄 ПЕРЕПИСАНО по твоему требованию

Мой прошлый текст был неверным (варианты A/B/C с флагами `--workers`). Убрала. Действует **только**
твоя схема: **любой параметр командной строки = поле конфигурации yaml**, никаких отдельных флагов
и никакой зависимости от порядка.

#### D12.1 Правило

```text
[путь_к_git]  +  -поле:значение …   (сколько угодно, порядок любой)
```

| Часть | Что | Обязателен | Порядок важен |
|---|---|---|---|
| **единственный позиционный** | **цель**: каталог · URL репозитория · URL организации · слово `yaml` | нет | идёт первым |
| `-поле:значение` | **любое** поле из `mdscan.yaml`, имя = путь в yaml через точку | нет | **нет** |

**Позиционный аргумент ровно один — цель.** Каталоги лога и отчёта не позиционные, они задаются
как обычные поля конфигурации:

```text
-logging.dir:out/hw01/logs        -report.dir:out/hw01/reports
```

Путаницы в последовательности нет: запоминать надо только одну позицию — цель,
всё остальное по имени, как в yaml.

#### 🔒 ЗАКОН CLI (записано дословно, без вариантов)

```text
1. Аргументов НЕТ           → печатаем конфигурацию и выходим, код 0.
2. Аргументов ≥ 1           → ПЕРВЫЙ аргумент ВСЕГДА цель (одна из 4 веток ниже).
3. Первый не подходит ни    → ошибка, выходим, код 2.
   под одну ветку
4. Все остальные аргументы  → только -поле:значение, порядок любой.
```

#### 🌿 Четыре ветки цели (первый аргумент)

| Ветка | Первый аргумент | Что сканируем |
|---|---|---|
| локальный каталог | путь (`E:\DSP-GPU`, `/home/alex/proj`) | папку на диске |
| один репозиторий | git-URL (`git@github.com:org/repo.git`, `https://…/repo.git`) | клонируем и сканируем |
| организация | URL организации (`https://github.com/dsp-gpu`) | все её репозитории (список — по `source.discovery`) |
| **`yaml`** ✅ решение Alex | буквально слово `yaml` | цель(и) из конфига: `source.target` + `source.repositories`. Заполнены оба → сканируем **всё вместе**; пусты оба → ошибка, код 2 |

```bash
python -m core.mdscan yaml                      # всё из конфига
python -m core.mdscan yaml -workers.parse:8     # из конфига + разовое переопределение
```

**Почему слово, а не символ `#`:** `#` в bash и PowerShell начинает комментарий — аргумент не
дойдёт до программы, пришлось бы всегда писать `'#'` в кавычках и ловить «почему печатает конфиг».
Слово `yaml` не конфликтует ни с одной оболочкой.

Никаких других трактовок первого аргумента не существует.

#### D12.2 Соответствие «yaml ↔ командная строка» (один в один)

| В `mdscan.yaml` | В командной строке |
|---|---|
| `source:`<br>` target: ''` | первый аргумент CLI подставляется в это поле |
| `logging:`<br>` dir: out/hw01` | `-logging.dir:out/hw01/logs` |
| `report:`<br>` dir: out/hw01` | `-report.dir:out/hw01/reports` |
| `workers:`<br>` parse: 5` | `-workers.parse:8` |
| `http:`<br>` timeout_ms: 2000` | `-http.timeout_ms:5000` |
| `progress:`<br>` enabled: true` | `-progress.enabled:false` |
| `scan:`<br>` include_nested_repos: false` | `-scan.include_nested_repos:true` |
| `logging:`<br>` level: INFO` | `-logging.level:DEBUG` |

Новое поле в yaml → **автоматически** доступно в командной строке. Отдельный код разбора для
каждого параметра писать не нужно: имя ищется в дереве конфига, тип берётся из значения по
умолчанию, неизвестное имя → ошибка с подсказкой «похожие поля».

#### 🔄 D15.1 Базовые классы и один объект-носитель данных (требование Alex)

> Alex: «создавай базовый класс, например к Observer, и наследуй класс для сбора данных в очередь.
> После разбора md значение можно присваивать классу, который дальше передаётся везде вплоть до
> формирования отчёта. Не нужно плодить сущности — посмотри внимательно».

**Принято, и это заметно сокращает число классов. Пересматриваю свой же проект.**

**(1) Базовый Observer + наследники** (Template Method + Observer):

```text
BaseObserver (абстрактный)
  ├ run()              шаблон: цикл get() → диспетчер → task_done() в finally → выход по сентинелу
  ├ on_item(item)      абстрактный — что делать с элементом
  ├ on_error(exc)      перехват и логирование (D2.1) — общий для всех
  └ on_finish()        завершение (сброс, статистика)
        ↑
        ├── MarkdownWorker       поток `parse-N` (× workers.parse): читает TaskQueue, сентинел
        │                        END_DISCOVERY; on_item(task) = прочитать → извлечь → проверить → put(result)
        └── CollectingObserver   поток `collector` (в D4 — «reporter»): читает ResultQueue, сентинел
                                 END_RESULTS; копит MdFileResult и кормит StatisticsCollector

Цикл, перехват исключений, `task_done()`, реакция на сентинел — **написаны один раз** в базовом
классе. Новый потребитель = наследник с одним методом. Это и есть «не плодить сущности».
🔧 ревью 2: `StatisticsObserver` и `LoggingObserver` убраны — статистику считает `StatisticsCollector`
внутри collector'а, лог пишут сами worker'ы (D2.1).
🔧 ревью 3: parse-worker — **тоже наследник `BaseObserver`** (он ровно такой же потребитель очереди с
сентинелом), а не отдельный `ThreadPoolExecutor`: иначе цикл `get → обработать → task_done → выход по
сентинелу` писался бы дважды, и правило «сентинел на каждый worker» (D3.1) реализовывалось бы двумя
способами. Отчёт и консоль строит **главный поток** после `join()` из `collector.results` +
`statistics.summary()` — collector сам ничего не пишет (D4).

**(2) Один объект-носитель, а не пять.** Здесь ты поймал реальное «барокко» в моём же проекте.
Было: `MdLink` → `MdFileResult` → `LinkStatus` → `ScanSummary` → ещё и «плоские строки» для отчёта.
Данные переливались из структуры в структуру.

Становится: **`MdFileResult` — единственный носитель**, который живёт до отчёта, обрастая
данными по пути (🔧 ревью 2, уточнение: discover кладёт в `TaskQueue` лёгкий `MdTask` — Command
с `RepoInfo` + путь; parse-worker создаёт из него `MdFileResult` и дальше носитель один):

| Этап | Кто пишет | Что добавляется в объект |
|---|---|---|
| постановка задачи | discover | `MdTask`: `repo` (`RepoInfo`), `md_file`, относительный путь |
| разбор | parse-worker | `MdFileResult(task)` + `links` (список `MdLink`), `error`, `seconds`, `thread_name` |
| проверка ссылок | checker (из parse-worker'а, до `put()` — D3.1 п.3) | статус в **самом** `MdLink` (`status: CheckStatus`, `detail`, `http_code`) |
| агрегация | observer | ничего не переписывает — только считает |
| отчёт | reporter | читает готовое |

Что из этого следует:
- **`LinkStatus` как отдельный класс убираю** — статус живёт полем внутри `MdLink`. Минус класс,
  минус перекладывание данных.
- «Плоскую таблицу» для отчёта не храним отдельно — строим на лету из `MdFileResult`.
- `ScanSummary` остаётся, но это уже **не** копия данных, а только числа-итоги.

#### D15.2 Правило владения данными (вместо «заморозки»)

Твоя формулировка верная, беру её: **достали, обработали, положили в очередь — забыли.**
Никаких копий, никакого `freeze()`. Механику заморозки из спеки убрала.

```text
поток-владелец                     очередь                другой поток
───────────────                    ───────                ───────────
создал MdFileResult
дописал ссылки, время, ошибку
    └── put(result) ──────────────►  [ … ]  ────────────►  get() → только читает
        владелец больше
        к объекту не обращается
```

Почему безопасно: гонка бывает, когда двое пишут одновременно или один пишет, пока другой читает.
Здесь ни того, ни другого: сначала пишет ровно один поток, потом только читают.
`queue.Queue` сама расставляет барьеры памяти — читающий видит финальное состояние.

Одно правило вместо трёх абзацев: **после `put()` объект не изменяется.**

**Про `ScanConfig` — ты понял правильно, это ровно то, что ты написал.**
`ScanConfig` — это объект в памяти, куда сложены значения из `mdscan.yaml` + переопределения из
командной строки. Собирается **один раз на старте** (фаза 0, D4), дальше потоки только читают.
Никто его не меняет — я просто фиксирую это как проверяемое требование:
`@dataclass(frozen=True)`, чтобы «случайная» правка из потока падала сразу, а не портила прогон.

| Объект | Когда пишется | Кто читает | Защита |
|---|---|---|---|
| `mdscan.yaml` | правит человек | загрузчик на старте | — |
| **`ScanConfig`** | один раз на старте | все потоки | `frozen=True` |
| `MdFileResult` | своим потоком-владельцем | после `put()` — читатели | правило владения |

**Про API «как в C#» — да, это правильная мысль, и она ложится на Python так:**

Аналог C#-интерфейса `IFoo` в Python — `typing.Protocol`. Отличие: наследоваться от него не
обязательно, достаточно совпадения методов (структурная типизация), а `mypy` всё равно проверит.
Префикс `I` не пишем — это не Java/C#, имя интерфейса просто существительное.

```python
# core/tokenstat/token_meter.py
class TokenMeter(Protocol):
    """Публичный контракт счётчика токенов — то, что видно снаружи."""

    def start(self, label: str) -> None: ...          # начать отсчёт (вызов скила)
    def mark(self, agent: str, task: str) -> None: ... # отметить работу агента
    def stop(self) -> None: ...                        # закончить отсчёт

    @property
    def total(self) -> TokenTotals: ...                # итог: in/out/cache/thinking
    def by_agent(self) -> dict[str, TokenTotals]: ...  # разбивка по агентам
    def report(self) -> str: ...                       # готовый Markdown
```

**Почему так, а не `set(...)`/`get(...)` как в C#:**

| C#-стиль | Python-стиль | Почему лучше здесь |
|---|---|---|
| `obj.SetWorkers(8)` / `int v = obj.GetWorkers()` | `obj.workers = 8` / `v = obj.workers` (через `@property`) | в Python геттер/сеттер — это свойство; лишние методы только шумят |
| `IFoo` | `class Foo(Protocol)` | не требует наследования, проверяется `mypy` |
| Явная реализация интерфейса | утиная типизация + `Protocol` | подменяется в тестах без каркаса моков |

✅ **Alex согласен на такой стиль API** (2026-08-16) — вношу в правило 09 как обязательное.

**Правило для всего проекта**: у каждого модуля есть **один** файл
`<name>_protocol.py` (или `Protocol` рядом с классом) — это и есть его публичное API. Всё
остальное — детали реализации. Наружу из пакета торчит только фасад в `__init__.py`.

Применение к нашим модулям:

| Модуль | Публичный контракт |
|---|---|
| `core/tokenstat` | `TokenMeter` |
| `core/mdscan` | `Scanner` (`scan(config) -> ScanSummary`) — файл `core/mdscan/scanner.py`, реализует `ScanOrchestrator` (🔧 ревью 3: в C4 было `run()` — приведено к `scan()`) |
| источники | `RepositorySource` |
| парсер | `LinkExtractor` |
| проверки | `LinkChecker` |
| вывод | `ConsoleRenderer`, `ReportBuilder` |
| потребители очередей | `BaseObserver` (очереди — stdlib `queue.Queue`, D2) |


### D19. Конфигурация: yaml + переопределение из командной строки (требование Alex)

> Alex: холодный старт → пишем параметры по умолчанию и формируем yaml; если запускаем со ссылкой
> на git и yaml нет — создаём его и используем значения по умолчанию. Если в yaml `поле1: значение`,
> то в командной строке `-поле1:новое значение`. Без ключей — вывести все конфигурации.

**Принято целиком.** Это снимает мой вопрос про «5 позиционных аргументов» (D12): параметров может
быть сколько угодно, и все переопределяются единообразно.

#### D19.1 Приоритет источников

```text
defaults (код)  <  mdscan.yaml  <  командная строка
```

- **Холодный старт** (yaml нет): берём defaults → **создаём `mdscan.yaml`** → работаем.
  В лог: `INFO: конфиг не найден, создан mdscan.yaml со значениями по умолчанию`.
- Запуск со ссылкой на git без yaml — тот же сценарий.
- yaml есть, но неполный → недостающее берётся из defaults; файл без спроса не переписываем.

#### D19.2 Разбор переопределений (механика; синтаксис и примеры — D12)

Здесь только то, что относится к **обработке** значения, пришедшего из командной строки:

| Шаг | Что делает загрузчик |
|---|---|
| 1. Разбор | режет `-<путь.к.полю>:<значение>` по **первому** двоеточию |
| 2. Поиск поля | идёт по дереву конфига через точку (`http` → `timeout_ms`) |
| 3. Проверка | поля нет → ошибка + «похожие поля: …», код `2`; опечатка не должна проходить молча |
| 4. Приведение типа | по типу значения по умолчанию: `int`, `float`, `bool` (`true/false/1/0`), `str`, список через запятую |
| 5. Запись | значение кладётся в итоговый `ScanConfig`, источник помечается как `c` (cmdline) |

Готовый `ScanConfig` собирается один раз и дальше не меняется (D15.2).
