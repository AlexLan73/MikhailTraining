## 3. Слои (прямые замеры `perf_counter`, без потоков)

Значения из прогона `--workers 1 --repeat 5 --layers`; слои считаются последовательно
и от `workers.parse` не зависят (проверено: заходы при 1/5/10 дали те же числа ±0.01 с,
кроме одного выброса `check_cold` 0.291 с при 5 потоках — фоновая нагрузка машины).

| Слой | Чем меряли | Замер | Ожидалось по спеке §2.2 | Доля от 0.605 с |
|---|---|---|---|---|
| Стадия 1: обход | `MarkdownFileFinder(заглушка, ('.md','.markdown'), False, False).find(RepoInfo(root=tree), [])` | **0.121 с** | 0.12 с | 20 % |
| Чтение 500 файлов | `MarkdownReader.read` в цикле | **0.025 с** | 0.03 с | 4 % |
| Извлечение ссылок | `MarkdownItLinkExtractor.extract` в цикле | **0.088 с** | 0.10 с | 15 % |
| Классификация | `LinkClassifier.default().classify` в цикле | **0.003 с** | <0.01 с | <1 % |
| Проверка, **холодный** кэш заголовков | свежий `CheckerFactory(config, MarkdownItHeadingSource(), NullNotifier())`, затем `for_kind(kind).check(link, path)` | **0.186 с** | 0.12 с | 31 % |
| Проверка, **тёплый** кэш (второй проход той же фабрикой) | то же, повторно | **0.078 с** | — | 13 % |
| → из них **второй разбор `markdown-it` ради заголовков** | холодный − тёплый | **0.108 с** | ≈0.10 с | 18 % |
| «Полезная нагрузка» последовательно | read + extract + classify + check одним циклом, свежая фабрика | **0.319 с** | 0.34 с | 53 % |
| Накладные (потоки, очереди, `join`, старт/стоп логгера, отчёт) | полный − обход − нагрузка | **0.166 с** | ≈0.13 с | 27 % |

Баланс сходится: `0.605 ≈ 0.121 (обход) + 0.319 (нагрузка) + 0.166 (накладные)`.

**Расхождение с ожиданием — одно**: «проверка» 0.186 с против 0.12 с. Причина — методика:
спека §2.2 получала это число **разностью прогонов** (`checks.local/anchors=false` минус полный),
здесь слой замерен **прямо**, поэтому в него вошли (а) собственное чтение файла внутри
`AnchorChecker._slugs_of` (он читает файл сам — `MarkdownReader` ему импортировать нельзя, §2.5
dev/test-спеки), (б) `resolve()`/`exists()` каждой локальной ссылки в `LocalFileChecker`.
Разложение прямого замера: 0.108 с — разбор заголовков, 0.078 с — файловые вызовы и повторное
чтение. Ключевое число спеки (≈0.10 с на заголовки) **подтверждено**; занижен был остаток
(0.02 с против фактических 0.078 с).

**Что это значит для H-05**: цель G-H (не разбирать файл вторично ради заголовков) стоит
**0.108 с ≈ 18 %** — самая крупная одиночная статья расходов. Цель G-D (обход без двойного
`resolve()`) сидит внутри 0.121 с обхода.

## 4. Профиль cProfile (справочно)

### 4.1 ⚠️ Оговорка: `cumtime` при потоках недостоверен

`cProfile` собирает записи со всех потоков в одну таблицу, а рекурсивная свёртка (`ncalls` вида
`4395/2394`) складывает `cumtime` повторно. Наблюдение из трёх прогонов, один и тот же вызов
`nt._getfinalpathname`:

| Прогон | Общее время под профайлером | `cumtime` у `_getfinalpathname` | Доля |
|---|---|---|---|
| `--workers 1` (а) | 1.208 с | **1.302 с** | **108 %** |
| `--workers 1` (б) | 1.365 с | 0.118 с | 9 % |
| `--workers 10` | 1.242 с | **2.563 с** | **206 %** |

Больше 100 % физически невозможно — это артефакт многопоточности (спека §2.1), и он **плавает**
от прогона к прогону. **Смотреть надо `tottime`**: он стабильно 0.16–0.18 с ≈ **13–15 %**, а не
63 %, как читалось из `cumtime` при первом анализе. Общее время под профайлером (≈1.2–1.4 с) вдвое
больше реального (0.60 с) — это накладные самого профайлера, поэтому доли из профиля переносить на
реальный прогон нельзя; для этого есть раздел 3.
