## 1. Как воспроизвести

```bash
python tests/hw01/support/bench_load.py --sizes 500,2000,5000 --workers 1,10 --repeat 5 --leak 5000 --log-run 5000
```

**Условия** (одинаковы во всех строках, конфигурация совпадает с `bench_scan.py` H-04):

| Параметр | Значение |
|---|---|
| Деревья | `FixtureTreeBuilder().generated(out/hw01/load/gen_<N>, N, 42)` — 500 / 2000 / 5000 файлов `.md` |
| Ссылок в дереве | 1025 / 3971 / 10087 (примерно 2 на файл: local + anchor + url) |
| Конфигурация | `scan.respect_gitignore=false`, `http.enabled=false`, `progress.enabled=false`, `logging.enabled=false`, `report.console=false`, `report.dir=out/hw01/load/out_<N>`, `run.fail_on_broken=false` |
| Время | 1 прогон прогрева + `--repeat` прогонов, берётся **медиана**; `time.perf_counter` вокруг `Scanner.scan` |
| Память | **отдельный** прогон под `tracemalloc`, пик = `get_traced_memory()[1]`; `tracemalloc` сам стоит ×2.3 по времени (тот же прогон: 3.5 → 8.2 с), поэтому в таблицу времени он не входит |
| Очереди | фоновый поток опрашивает `ScanOrchestrator.snapshot()` (он же `ProgressSource`, T-11) каждые **50 мс**, копятся максимумы `task_qsize`/`result_qsize` |
| Машина | Windows 11 (10.0.22000), Python 3.14.0 x64, `.venv` в корне репозитория |

⚠️ **Шум**: замер шёл **параллельно с таском H-07** (в системе висели 3 сторонних процесса `python.exe`,
один — 270 МБ RSS). Первый заход дал на 5000 файлов / 1 поток **3.92 с**, спокойный заход с `--repeat 5` —
**3.26 с**: разброс до 20 % на однопоточных строках. Все выводы ниже сделаны по заходу `--repeat 5`;
однократные числа в этом документе не используются.

## 3. Ответы на вопросы таска

### 3.1 Линейно ли растёт время? — Да, строго линейно (r² = 0.99997)

Линейная регрессия по трём точкам (`workers.parse=1`):

```text
время(N) = 0.078 с + 0.636 мс × N      r² = 0.99997
время(N) = 0.078 с + 0.685 мс × N      r² = 1.00000   (workers.parse=10)
```

- отношения времени: 500→2000 (×4 файлов) = **×3.49**; 2000→5000 (×2.5) = **×2.39**; 500→5000 (×10) = **×8.35**;
- цена одного файла даже **падает** с ростом дерева: 0.780 → 0.680 → 0.651 мс — это амортизация постоянной
  части (старт/стоп потоков и логгера, сборка конфигурации, запись отчёта ≈ 0.08 с);
- пропускная способность растёт 1283 → 1471 → 1536 файлов/с и выходит на плато.

Вывод: масштабирование **чуть лучше линейного** (sub-linear), квадратичных мест нет — ни в реестре
обработанных путей (`ProcessedRegistry` — множество, O(1) на файл), ни в обходе, ни в сборке отчёта.
Экстраполяция: 50 000 файлов ≈ **32 с**, 100 000 ≈ **64 с** (без HTTP).

### 3.2 Не течёт ли память? — Нет

Три прогона подряд по 5000 файлов в **одном** процессе (`--leak 5000 --leak-times 3`, `tracemalloc`,
`gc.collect()` после каждого, `reset_peak()` перед каждым):

| Прогон | Остаток после прогона (`current`) | Пик (`peak`) |
|---|---|---|
| 1 | 0.1 МиБ | 28.0 МиБ |
| 2 | 0.1 МиБ | 28.0 МиБ |
| 3 | 0.1 МиБ | 28.0 МиБ |

Остаток не растёт, пик воспроизводится до десятой доли МиБ → между прогонами ничего не удерживается.
Это ожидаемо по архитектуре: `PipelineRunner` создаётся заново на каждый `scan()`, а
`ScanOrchestrator._shutdown` обнуляет ссылку на него (`self._pipeline = None`), так что результаты,
очереди и кэши чекеров умирают вместе с конвейером.

Пиковая память тоже линейна:

```text
память(N) = 1.6 МиБ + 4.6 КиБ × N     (workers.parse=1,  r² = 1.00000)
память(N) = 5.0 МиБ + 4.6 КиБ × N     (workers.parse=10, r² = 1.00000)
```

Наклон от числа потоков **не зависит** (4.6 КиБ на файл — это данные), постоянная часть растёт
на 3.4 МиБ при 10 потоках: свой `MarkdownIt`, свой набор чекеров и кэш заголовков на каждый worker.

### 3.3 Не переполняются ли очереди? — Не переполняются (они безграничные), но backlog = всё дерево

`TaskQueue`/`ResultQueue` — псевдонимы `queue.Queue` **без `maxsize`** (`runtime/queues.py`), обратного
давления в конвейере нет по проекту: завершение идёт только по сентинелам, а `qsize()` разрешён
исключительно для строки прогресса (dev/test-спека §2.2). Поэтому «переполниться» очередь не может —
вопрос в том, сколько в ней копится.

| файлов | пик `task_qsize` | доля дерева | пик `result_qsize` |
|---|---|---|---|
| 500 | 440 | 88 % | 1 |
| 2000 | 1884 | 94 % | 13 |
| 5000 | 4879 | 98 % | 17 |

```text
пик task_qsize(N) = 0.988 × N − 69     r² = 0.99992
```

**Почему копится всё дерево**: стадия 1 (обход + `resolve()` + реестр) после H-05 стоит ≈0.06 с на
500 файлов, а разбор одного файла — ≈0.6 мс; поставщик быстрее потребителя примерно в 10 раз, поэтому
к моменту, когда воркеры разберут первые сотни файлов, обход уже поставил в очередь остальные.
При 10 потоках пик чуть ниже (4319 против 4879) — потребители успевают снять больше.

`result_qsize` всегда ≈ 0: `CollectingObserver` забирает результаты сразу, но **держит их в списке**
до конца прогона (они нужны отчёту). Так что пиковые 24.6 МиБ на 5000 файлов — это в основном
`MdFileResult` со ссылками, а не сами `MdTask`.

Практический смысл: backlog и память растут линейно ~**4.6 КиБ на файл**, потолок задаётся объёмом
дерева, а не размером очереди. 100 000 файлов → ≈ **0.5 ГБ** пиковой памяти. Это ограничение, а не
поломка: перед клиентом с монорепо такого размера решение (batch-отчёт / `maxsize` очереди
с обратным давлением) должен принимать Alex — это трогает D1/D3, менять по своей инициативе нельзя.

### 3.4 Что ломается на 5000? — Ничего не ломается

Пять заходов подряд, 30+ прогонов дерева 5000 файлов: ни одного исключения, ни одной строки
`ERROR`/`CRITICAL` в логе, код возврата 0 (`fail_on_broken=false`), отчёт полный (7 784 строки,
все 2699 битых ссылок перечислены), потоки завершаются штатно, `join` по таймауту ни разу не сработал.
`pytest tests/hw01 -q` после замеров — **427 passed, 4 skipped**.

## 5. Масштабирование потоков: 1 против 10

| файлов | 1 поток | 10 потоков | `speedup` |
|---|---|---|---|
| 500 | 0.390 с | 0.418 с | **0.933** |
| 2000 | 1.360 с | 1.451 с | **0.937** |
| 5000 | 3.255 с | 3.501 с | **0.930** |

`speedup` **не зависит от размера дерева** и совпадает с базой H-04 (0.921 на 500 файлах): накладная
часть потоков масштабируется ровно пропорционально объёму работы, «с ростом дерева станет хуже» —
не подтвердилось. Причина `speedup < 1` — та же, что в спеке §2.3: без HTTP нагрузка CPU-bound под
GIL, плюс постоянные 3.4 МиБ и 10 наборов чекеров на старте. С включённым HTTP картина обратная
(H-07), здесь сеть выключена намеренно.

Промежуточный заход, когда параллельно работал H-07, показывал 10 потоков «быстрее» одного
(3.46 против 3.92 с) — это был шум чужой нагрузки, спокойный заход с 5 прогонами его снял.
Отмечено отдельно, чтобы число не всплыло позже как «противоречие».
