## 2. Анализ тонких мест — по замерам, а не по догадкам (🔧 р6: переписано)

Набор B (500 файлов, 1025 ссылок), `workers.parse=1`, HTTP/лог/прогресс/консоль выключены, Windows,

### 2.1 ⚠️ Почему первая картина («63 % — `Path.resolve()`») была ошибочной

Профиль `cProfile` действительно показывает `nt._getfinalpathname` с `cumtime` ≈ 1.3 с при общем времени
≈ 1.26 с — то есть **больше 100 %**. Это артефакт: `ncalls 4395/2249` — рекурсивная свёртка вызовов из
**разных потоков** (parse-worker + collector + главный), `cumtime` у неё складывается повторно.
Честная величина — `tottime` = **0.16 с ≈ 13 %**, а не 63 %. Вывод «узкое место — `resolve()`» —
**неверен**; H-05 в прежней формулировке лечил бы не то.

### 2.2 Прямые замеры по слоям (`time.perf_counter`, без профайлера)

Полный прогон `workers.parse=1`: **0.59 с**; `workers.parse=5`: **0.63 с**; `=10`: 0.66 с
(🔧 р6: по решению Alex умолчание `workers.parse` и `http.workers` поднято 5 → **10**: с HTTP 10 потоков дают ×10.6
на локальном сервере с задержкой 30 мс, без HTTP цена +8 %).

| Слой | Как мерил | Время | Доля |
|---|---|---|---|
| Стадия 1: обход (`rglob` + `resolve()` каждого файла + реестр) | `MarkdownFileFinder.find` отдельно | 0.12 с | 20 % |
| Чтение 500 файлов | `MarkdownReader.read` в цикле | 0.03 с | 5 % |
| Извлечение ссылок (`markdown-it-py`) | `MarkdownItLinkExtractor.extract` в цикле | 0.10 с | 17 % |
| Проверка локальных + якорей, из них **второй разбор `markdown-it` ради заголовков** (`AnchorChecker` → `MarkdownItHeadingSource`) | прогон с `checks.local/anchors=false` минус полный; повтор с тёплым кэшем заголовков | 0.12 с (≈0.10 — заголовки, ≈0.02 — `resolve/exists`) | 20 % |
| Классификация | цикл | <0.01 с | — |
| Накладные (потоки, очереди, `join`, старт/стоп логгера) | остаток | ≈0.13 с (при 5 потоках +0.04) | 22 % |
| Отчёт `MarkdownReportBuilder.build` | обёртка | 0.004 с | <1 % |

Последовательная «полезная нагрузка» без потоков (read + extract + classify + check по всем файлам): **0.34 с**;
с тёплым кэшем заголовков — 0.23 с. Значит: 0.59 ≈ 0.12 (обход) + 0.34 (нагрузка) + 0.13 (накладные).

### 2.3 Почему потоки не дают ускорения

1. Полезная нагрузка — чистый Python (`markdown-it` дважды на файл) → **GIL**: 5–10 потоков делят один процессор
   (замер: 1/2/5/10 потоков → 0.61/0.60/0.65/0.66 с).
2. Файловые вызовы (`resolve`, `exists`, `open`) — короткие и кэшируются ОС; ждать на них почти нечего.
3. Очередь/`task_done`/переключение на 500 мелких задач — +0.04 с при 5 потоках.

Итог: `speedup < 1` без HTTP — закономерность для CPU-bound нагрузки под GIL. Потоки окупаются, когда
воркеры **ждут** — сеть (`HttpChecker`); это подтверждает и боевой прогон (67 с на 1230 файлов при
включённом HTTP, где основное время — ответы серверов).
